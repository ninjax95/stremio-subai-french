### Override systemd Ollama (optimisation Strix Halo)

Fichier : `/etc/systemd/system/ollama.service.d/override.conf`

```ini
[Service]
Environment="HSA_OVERRIDE_GFX_VERSION=11.5.1"
Environment="OLLAMA_FLASH_ATTENTION=1"
Environment="OLLAMA_KEEP_ALIVE=10m"
```

- `HSA_OVERRIDE_GFX_VERSION=11.5.1` : indispensable pour gfx1151 (Strix Halo)
- `OLLAMA_KEEP_ALIVE=10m` : déchargement auto après 10 min d'inactivité (évite que les modèles testés bouffent toute la RAM)

## Choix du modèle (parcours)

Tests effectués pour trouver le bon compromis qualité/vitesse sur Strix Halo :

| Modèle | Vitesse | Qualité | Verdict |
|---|---|---|---|
| `mixtral` (ancien défaut) | non testé | — | trop lourd, abandonné |
| `llama3.1:70b` (Q4, 42 Go) | **3 t/s** ⚠️ | ⭐⭐⭐⭐⭐ | trop lent (memory-bandwidth bound sur Strix Halo) |
| `qwen3:30b-a3b` base | 33 t/s mais "thinking" génère 1500-2000 tokens parasites | ⭐⭐⭐⭐⭐ | inutilisable tel quel |
| `qwen3:30b-a3b-instruct-2507-q4_K_M` | **30 t/s, sans thinking** | ⭐⭐⭐⭐⭐ | ✅ **CHOISI** |

**Pourquoi qwen3 30B MoE > llama 70B dense sur Strix Halo :**
- Strix Halo a ~256 GB/s de bande passante mémoire (vs 1000+ GB/s GPU dédié)
- Pour un modèle dense 70B Q4 (40 Go) : max théorique = 40/256 = 6.4 t/s
- Pour un MoE 30B avec 3B actifs/token : seuls les experts utiles sont lus → 10x plus rapide
- C'est pour ça qu'AMD recommande des MoE sur Strix Halo

**Estimation pour un film entier (~1500 lignes) :** ~8 min de traduction (vs ~85 min avec llama 70B).

```bash
curl -s http://127.0.0.1:11434/api/ps | python3 -m json.tool
```

### Problème connu

Sur ce hardware, **éviter les modèles 70B dense** (memory-bandwidth bound). Préférer **MoE** (Qwen3, GLM, Llama 4 Scout) ou **modèles ≤ 32B**.
